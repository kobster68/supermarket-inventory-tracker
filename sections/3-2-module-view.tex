\subsubsection{View description}
This is the primary view of the architecture: the code structure as a hierarchy of
modules related by is-part-of, close to a domain model, from which the runtime components
of the key view grow. It conforms to the module decomposition viewpoint of the SEI Views
and Beyond template, whose element type is the module and whose relation is is-part-of
(``Software Architecture Document Template,'' \S\,Module Decomposition Viewpoint; Bass,
Clements, and Kazman 10--11). It shows the units a developer works in --- the Store
Subsystem, the \CFE, the Distribution Center Subsystem and a Common module of shared code
--- and which runtime component each realises, so the code and runtime structures can be
read against each other.

\paragraph{Domain model.}
The Common module's Domain Model is decomposed in Figure~\ref{fig:domain-model}, a class
diagram of the shared domain types. The product catalog uses the GoF Composite pattern: an
abstract \texttt{CatalogItem} with a recursive \texttt{totalValue()} operation,
\texttt{ProductFamily} as the composite and \texttt{Product} as the leaf. Product-to-family
membership is many-to-many, so a product may belong to several families, and the family
total-value report counts it once per family. An \InventoryEvent carries its source,
product, sequence and quantity delta; an InventoryLevel is the stock of one product at one
store or \DC; a \ShippingOrder carries lines of product and quantity with a status, raised
at a store and fulfilled by the \DC; and a report is one of the three the brief names.
Every association carries multiplicities.

\paragraph{Relations.}
\emph{Is-part-of} is the nesting in Figure~\ref{fig:module-decomposition}: each sub-module
is part of its subsystem. \emph{Uses} is the six dashed arrows: the Store Subsystem, the
\CFE and the Distribution Center Subsystem each use the Common Domain Model; the Store and
Distribution Center subsystems additionally use the \IEP library; and the external
\AnalyticsClient uses the \IEP library from outside the system. No other module-to-module
dependency exists.

\paragraph{Interfaces.}
The only interface a module view fixes is the provided interface of the \IEP library, the
full specification of Section~\ref{sec:iep}; the other shared contract is the set of
domain types in Figure~\ref{fig:domain-model}.

\paragraph{Behavior.}
A module view records no runtime behavior; the event flow and the outage-and-replay
behavior are documented in the Components-and-Connectors view (Section~\ref{sec:cc-view}).

\paragraph{Constraints.}
\begin{itemize}[nosep]
  \item The Common module depends on none of the subsystems; every dependency points into
  Common, never out of it.
  \item The Store Subsystem does not depend on the Distribution Center Subsystem (only on
  Common), so a store can be built, tested and deployed on its own.
  \item Each runtime component of the Components-and-Connectors view is realised by exactly
  one module.
\end{itemize}

\subsubsection{Context diagram}
The module view shares the system boundary of the key view, fixed by the context diagram
of the Components-and-Connectors view (Figure~\ref{fig:cc-context}) and not repeated here;
the external POS system is reached only through the \POSAdapter module, and the external
\AnalyticsClient attaches from outside through the Common module's \IEP library.

\subsubsection{Variability mechanisms}
\label{sec:module-variability}
\begin{itemize}[nosep]
  \item \emph{A new client type:} a new sub-module of the Distribution Center Subsystem
  that uses the \IEP library, with no change to existing modules (\scnref{MOD-1},
  \scnref{INT-2}).
  \item \emph{Deeper product families:} nesting depth lives in the composite in the domain
  model, so a new level is a data change, not a module change (\scnref{MOD-2}).
  \item \emph{More stores:} not a module concern --- every store is the same Store
  Subsystem, so the chain grows by instances, not modules (\scnref{SCAL-1}).
  \item \emph{A new platform:} platform-specific code is confined to the \POSAdapter and
  the \IEP library's wire binding, so a port touches only those.
\end{itemize}

\subsubsection{Architecture background}
This decomposition is organised for modifiability, the quality the decomposition structure
most directly determines (Bass, Clements, and Kazman 10), using three coupling-reducing
tactics (Bass, Clements, and Kazman 123--124): \emph{encapsulate} (each subsystem hides
its internals and platform-specific code is confined to the adapters), \emph{use an
intermediary} (the \IEP library carries events between the Store and Distribution Center
subsystems, so neither depends on the other), and \emph{restrict dependencies}
(dependencies run one way, into Common, so a store builds and deploys alone and a new
client is added without touching existing modules).
